# Kagent 前端页面设计与开发指南 (Page Guide)

本文件是 `kagent` 全站页面的基础风格与前端开发规范，重点约束后台管理类页面（admin-style pages）的视觉与交互一致性，同时对所有页面统一要求纯原生、自包含、模块化与可维护性。`webui/page/service/admin.html` 仅作为已落地参考，不是模板页面，更不是必须照搬的布局答案。

## 1. 文档定位

本指南服务于两个层面：

- 页面风格层：定义全站页面，尤其是后台管理页，应共享的视觉语言、信息层级和交互逻辑。
- 技术实现层：定义全站统一的前端开发方式，包括纯原生、自包含、模块化、资源组织与文件拆分规则。

本指南不是某个单页的实现说明。任何页面都可以根据任务目标自由设计主要内容区，只要不破坏本文件定义的统一气质、信息组织质量和工程边界。

---

## 2. 设计目标

Kagent 页面默认追求以下特征：

- 清晰：层级分明，主次关系明确，核心操作容易发现。
- 专业：技术对象、状态、协议、路径、配置等信息应具备工程感与可信度。
- 克制：不过度装饰，不过度强调品牌感，以可操作性优先。
- 统一：不同页面可有布局差异，但视觉令牌、组件气质和交互逻辑应保持同源。
- 本地优先：页面在没有外部资源支持时仍应完整可用。

---

## 3. 适用范围

默认适用于：

- `webui/page/` 下所有 HTML 页面
- 后台管理类页面、服务治理页、工具管理页、配置管理页
- Surface 插件的独立管理面板
- 纯 HTML + CSS + ES Module 页面

不适用于：

- 非页面型 Markdown 文档
- 一次性调试页或临时实验页

---

## 4. 页面风格基线

### 4.1 整体气质

后台页面应体现“轻控制台”风格：

- 以浅色背景、白色卡片、细边框、有限阴影构建层次。
- 强调数据、状态和操作，不强调营销式视觉。
- 通过微弱动画和明确状态色传达系统活性，而不是靠大面积高饱和色块。

### 4.2 视觉令牌

当前推荐色盘基于已有页面样式抽取，作为全站默认基线：

| 变量名           | 色值      | 用途                   |
| :--------------- | :-------- | :--------------------- |
| `--bg`           | `#f3f4f6` | 页面背景               |
| `--card`         | `#ffffff` | 卡片、表格、浮层背景   |
| `--text`         | `#111827` | 正文与主标题           |
| `--muted`        | `#6b7280` | 次级说明、静默信息     |
| `--line`         | `#e5e7eb` | 分割线、描边、输入边框 |
| `--accent`       | `#0d9488` | 页面主强调色           |
| `--accent-hover` | `#0f766e` | 强调色悬停态           |
| `--accent-light` | `#f0fdfa` | 高亮底色、浅提示区     |
| `--ok`           | `#16a34a` | 成功、健康、运行中     |
| `--warn`         | `#d97706` | 警告、待处理           |
| `--err`          | `#dc2626` | 错误、危险操作         |

要求：

- 后台类页面默认只设一个主强调色，不混入多套品牌色。
- 危险色仅用于错误、删除、下线、不可逆操作。
- 不使用高饱和纯色大面积铺满背景。

### 4.3 圆角、阴影与边界

- `--radius-sm: 8px`
- `--radius-md: 12px`
- `--radius-lg: 16px`
- 卡片、表格、输入区优先使用细边框与轻阴影，而不是厚重投影。
- 浮层允许更高层级，但不要产生“营销弹窗”观感。

### 4.4 字体规范

- **字体系列**：
  - 正文与标题：`Inter`, `PingFang SC`, `system-ui`, `sans-serif`
  - 等宽内容：`JetBrains Mono`, `monospace`
- **字号统一标准**：
  - 基础默认大小：`14px` (在 `body` 中唯一定义)
  - 小字/辅助信息：`0.8rem` (用于标签、注释、表格表头、附属说明等)
  - 标题/主要名称：`1.2rem` (用于模块标题、服务名称、详情页数字显示等)
  - 特殊突出数字：`2rem` (仅用于概览看板中需要极致视觉冲击的特大数值)
- **约束要求**：
  - 正常文字内容不得出现上述标准之外的字号。
  - 按钮、输入框、常规列表项应自然继承基础字号，不重复声明。
  - 严禁在 CSS 中零散硬编码 `12px`、`13px` 等 ad-hoc 字号。

以下内容必须使用等宽字体：

- 服务 ID、工具 ID、任务 ID
- 文件路径、URL、Endpoint、版本号、PID
- JSON、Schema、配置片段、日志、命令字

### 4.5 文案风格

- 以中文为主，技术术语可中英并列。
- 操作按钮使用明确动词，避免“处理一下”“继续”等模糊表达。
- 状态文案短而稳定，避免同一系统内同义词乱飞。

## 5. 后台管理页的布局原则

### 5.1 原则

后台页需要统一的是“信息组织逻辑”，不是某个固定布局。

必须统一的内容：

- 页面有清晰的一级信息结构
- 全局操作与局部操作边界清楚
- 详情编辑、创建流程、危险操作的容器职责清楚
- 状态反馈位置稳定，用户能快速判断当前系统是否正常

允许自由变化的内容：

- 主内容区可以是表格、卡片矩阵、分栏面板、树形区、时间线或它们的组合
- 不同页面可以有不同密度和不同主视图
- 不要求所有页面都使用与 `service/admin.html` 相同的主内容布局

### 5.2 `admin` 页面作为参考的意义

`webui/page/service/admin.html` 当前只提供以下参考：

- 后台治理页可采用顶部全局头部 + 主内容区 + 次级浮层的结构
- 抽屉适合承载单实体详情工作区
- 弹窗适合承载创建类或短流程任务
- 模板化渲染适合承载复杂子面板

它不提供以下硬约束：

- 不要求所有页面都必须有双 Tab
- 不要求所有页面主区域都必须是表格
- 不要求所有页面都必须有 Drawer + Modal 双浮层
- 不要求照搬 `service/admin.html` 的 DOM 层级和布局比例

### 5.3 推荐信息结构

后台页通常应具备以下层级中的若干项：

1. 页面级概览：标题、摘要、全局状态、主要入口动作。
2. 任务级主视图：列表、卡片、面板、树或流程区。
3. 对象级详情区：用于查看单个实体的完整信息与可编辑字段。
4. 结果反馈区：用于显示运行结果、日志、Schema、空状态或错误信息。

页面设计时优先保证层级清楚，而不是先决定用哪种容器。

## 6. 统一交互逻辑

### 6.1 全局与局部操作分离

- 页面级动作放在稳定位置，例如头部或概览区。
- 行内动作、对象级动作、编辑保存动作应收敛到对象上下文内。
- 不要把“刷新全局列表”和“保存当前对象”做成同一层级的按钮群。

### 6.2 详情容器选择

- Drawer：适合上下文仍然留在当前页面内的详情查看、配置修改、对象治理。
- Modal：适合创建、确认、短向导、危险动作确认。
- 行内展开：适合快速查看补充信息，不适合承载复杂编辑流程。

### 6.3 状态反馈

页面必须具备以下反馈能力：

- 刷新中、加载中、提交中
- 成功、失败、空状态
- 运行中、停止、离线、异常等系统状态

要求：

- 同类状态在不同页面使用相同颜色与相近文案。
- 失败不能静默。
- 危险动作必须有视觉区别。

### 6.4 交互动效

- 默认过渡曲线：`cubic-bezier(0.4, 0, 0.2, 1)`
- 默认时长：`200ms ~ 400ms`
- 动效只用于强化状态变化、层级变化和操作反馈
- 禁止为“看起来高级”而堆叠无意义动画

### 6.5 页面提示与弹窗约束

- 页面内部的瞬时反馈必须接入统一的 `toast` 提示机制；成功、失败、警告、信息提示都应复用同一套组件、调用入口和样式语言。
- `toast` 组件必须由项目内部参照本规范的视觉令牌、层级、动效与交互约定自行实现，不得直接依赖系统原生提示样式，也不得每个页面各写一套提示 UI。
- 所有弹窗类交互都必须使用项目内部自定义样式的定制弹窗，包括但不限于消息提示、警告、确认、输入、短流程向导与危险操作确认。
- 禁止直接使用系统自带的 `alert()`、`confirm()`、`prompt()` 以及未定制样式的原生弹窗能力作为正式页面交互。
- 自定义弹窗必须与全站视觉风格一致，并明确区分信息提示、确认动作、危险确认、表单输入等场景，不得只做一个样式粗糙的通用壳。
- 新页面或重构页面在设计交互反馈时，优先复用内部 `toast`、`modal`、`drawer` 等基础组件；如需新增弹窗变体，也必须在本规范的视觉与交互约定内扩展，而不是绕开统一机制。

## 7. 纯原生与自包含原则

这是全站硬约束，不因页面类型变化。

### 7.1 纯原生

- 禁止引入 React、Vue、jQuery、TailwindCSS 等框架性依赖。
- 页面逻辑基于原生 ES Module。
- DOM 操作使用标准 Web API。
- 异步请求使用 `fetch` 与 `async/await`。

### 7.2 自包含

- 页面默认不依赖外部 CDN、外部字体、外部图标库、外部脚本。
- 页面应在离线或弱网络环境下仍可正常渲染和操作。
- 如确需外部资源，必须有本地替代方案或清晰降级策略；默认仍视为例外而非常态。

### 7.3 资源组织

- HTML、CSS、JS 文件应跟页面或模块一起存放，便于独立维护。
- 图标优先使用内嵌 SVG。
- 不使用 Emoji 作为正式功能图标。
- 不依赖外链图片承载关键功能语义。

---

## 8. HTML / CSS / JS 拆分规则

### 8.1 HTML 与 CSS 必须拆分

- 页面结构写在 HTML。
- 页面样式写在同名的独立 CSS 文件。
- 不允许把大段样式直接塞进 HTML。

少量内联样式只允许用于：

- 临时调试
- 极少数动态尺寸或运行时计算值

原则上应尽快回收到 CSS 类中。

### 8.2 CSS 可以继续模块化拆分

当页面样式较多时，允许并推荐拆分多个 CSS 文件，放到styles文件夹内，例如：

- `tokens.css`
- `layout.css`
- `components.css`
- `admin-page.css`
- `drawer.css`
- `modal.css`

拆分要求：

- 先抽公共 token，再抽通用组件，再写页面特有样式
- 不做无意义碎片化拆分
- 文件命名应直接表达职责

### 8.3 HTML 职责

HTML 负责：

- 页面骨架
- 语义结构
- 挂载点与模板
- 稳定 ID 和清晰层级

HTML 不负责：

- 大量业务判断
- 请求流程
- 复杂状态管理

### 8.4 CSS 职责

CSS 负责：

- 设计令牌
- 组件样式
- 状态类
- 布局规则
- 动效与响应式

CSS 要求：

- 能用类表达的状态，不要依赖大量运行时内联样式
- 公共样式优先复用，不重复复制

### 8.5 JS 职责

JS 负责：

- 请求和数据流
- 状态管理
- 模板渲染
- 事件绑定
- 页面初始化

JS 不负责：

- 承担大块静态结构定义
- 用脚本硬编码全部视觉样式

## 9. 模块化规则

模块化是全站原则，不要求只有一种拆法，但必须有清晰边界。

### 9.1 允许的拆分方式

#### A. 按功能分层

适合中小型页面：

- `api.js`
- `logic.js`
- `state.js`
- `render.js`
- `utils.js`
- `page-entry.js`

#### B. 按渲染块拆分

适合复杂页面：

- `toolbar.js`
- `overview-panel.js`
- `services-table.js`
- `config-drawer.js`
- `create-modal.js`

#### C. 混合拆分

推荐用于复杂管理后台：

- 请求与状态集中管理
- 各面板、抽屉、弹窗独立为渲染模块
- 页面入口只负责装配、路由和初始化

### 9.2 无论如何拆，都必须满足

- 请求入口集中，不能每个模块各自拼协议与接口细节
- 状态来源集中，避免多份真相
- 渲染逻辑和业务逻辑分离
- 事件绑定位置明确，便于排查
- 模块职责能从文件名直接看出来
- 单文件过大时应主动拆分，不把页面做成一个巨型脚本

### 9.3 模板化约定

推荐采用“骨架 HTML + `<template>` + 模块渲染”的方式：

- 稳定结构放 HTML
- 可切换子面板放模板
- 渲染后立即绑定局部事件

但模板只是手段，不是目标。简单区块不必为了模板而模板化。

## 10. 统一视觉与交互的最低要求

任何新页面都应满足：

1. 视觉令牌与全站一致，不私自发明一整套颜色和阴影。
2. 技术数据使用等宽字体，不混入普通正文字体。
3. 操作按钮分层清楚，主次明确。
4. 状态颜色与状态文案统一，不同页面不自创含义。
5. 空状态、错误态、加载态、成功反馈齐全。
6. 详情查看、编辑、创建、确认四类场景的容器职责清楚。
7. 页面提示统一走内部 `toast` 机制，不使用系统原生提示框顶替正式反馈。
8. 弹窗、确认、输入等浮层统一走内部定制组件，不使用系统 `alert` / `confirm` / `prompt`。
9. 页面在不依赖外部资源时仍可运行。
10. HTML、CSS、JS 各司其职，且支持继续拆分维护。

---

## 11. 评审清单

新增或重构页面时，至少核对以下问题：

1. 这个页面是否延续了全站统一的视觉语言，而不是另起炉灶。
2. 主内容区是否根据任务自由组织，而不是机械照搬别的页面。
3. 是否把 `admin` 仅当作参考，而不是复制它的具体布局。
4. 是否做到纯原生、自包含、无外部依赖。
5. 是否把 HTML、CSS、JS 拆分清楚。
6. CSS 是否独立成文件；样式复杂时是否继续合理拆分。
7. JS 是否保持模块化，状态、请求、渲染是否边界清晰。
8. 交互反馈是否完整，尤其是失败和空状态。
9. 是否统一复用了内部 `toast` 机制，而不是散落使用系统提示或页面私有提示样式。
10. 是否避免使用系统 `alert` / `confirm` / `prompt`，并将确认、输入、警告流程落在内部定制弹窗内。

---

本指南是全站页面基线。更新时优先维护“统一原则”和“工程边界”，不要把某个页面的当前实现误写成全站唯一答案。
