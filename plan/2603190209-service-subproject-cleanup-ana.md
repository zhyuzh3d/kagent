# Service 子项目清理通用分析

> 文档类型：分析（ana）  
> 时间：2026-03-19 02:09 CST  
> 范围：适用于任意独立 `service` 子项目的冗余清理、子系统收缩与残留收口  
> 目标：把“清理 service 子项目”抽象成一套可复用的判断框架，而不是只针对某个项目的具体文件名或目录结构

## 0. 核心结论

清理一个 service 子项目，不是做目录整理，而是收缩到“当前 binary 的最小可达集”。

1. 先看入口能到哪里，再看哪些代码真的会被执行。
2. 能删的不是“看起来旧”的代码，而是“从入口不可达、又不支撑当前能力或生命周期”的代码。
3. 对混合文件要拆着看：只删死分支，不要把仍在用的共享 helper 一起带走。
4. 整套未接入的子系统最值得先删，收益大、风险低。

## 1. 通用判断框架

### 1.1 先分三类

把 service 子项目中的代码先分成三类：

1. 对外能力实现
   - 例如 tool、API、RPC、handler、command、stream。
   - 这类代码直接决定 service 对外提供什么。
2. 生命周期支撑
   - 例如启动、注册、健康检查、退出、日志、存储、配置、路由。
   - 这类代码不一定对应某个具体能力，但通常是当前 binary 必需的。
3. 历史残留
   - 和当前能力无关，也不支撑当前生命周期。
   - 这类代码最适合清理。

### 1.2 判定原则

一个文件或代码块只有在满足以下任一条件时，才值得保留：

1. 从当前入口可达。
2. 为当前保留代码提供共享类型、共享 helper 或共享基础设施。
3. 属于当前 service 的生命周期必需部分。

不满足以上条件的内容，默认列为清理候选。

## 2. 最快的清理路径

### 2.1 先锁入口

先确认当前 service 的真实入口：

1. `main`。
2. 启动脚本。
3. 路由注册点。
4. 任务分发入口。

如果入口都没接上，后面再多的文件关联也只能算“静态存在”，不能算真实使用。

### 2.2 再列能力面

把当前 service 实际提供的能力列出来，按“tool / API / handler 名称”而不是文件名列。

这样做的目的：

1. 先知道什么是保留范围。
2. 再判断哪些文件只是旧实现。
3. 避免把支撑能力的基础文件误删。

### 2.3 做符号反查

对每个可疑文件的顶层符号做反查：

1. 查它有没有被入口链引用。
2. 查它有没有被仍在用的共享模块引用。
3. 查它是不是只有自己内部引用，且入口没有接线。

如果一个模块只在自己文件组里打转，但入口并没有接上，通常就是整套残留子系统。

### 2.4 优先删整套子系统

最容易清理的是“完整但未接入”的子系统。

典型特征：

1. 文件之间互相依赖。
2. 看起来结构完整。
3. 但入口没有把它们串起来。

这种情况不要一页页拆，直接按整套删除，风险更小。

### 2.5 混合文件拆分处理

混合文件是最容易误删的地方。

处理顺序建议是：

1. 先找出当前仍在用的 helper。
2. 把 helper 挪到仍保留的公共文件。
3. 再删 dead branch、dead method、dead protocol。

不要先删整文件再回头补缺失 helper。

## 3. 常见误区

### 3.1 把“不是 tool”误判成冗余

不是所有不直接处理 tool 的代码都能删。

很多 service 仍需要：

1. 启动和退出逻辑。
2. 注册和心跳。
3. 配置加载。
4. 存储和状态管理。
5. 日志和错误封装。

这些代码不一定暴露成对外能力，但它们可能是当前 binary 存活所必需的。

### 3.2 把“未来可能会用”当作保留理由

“以后也许会用”不能作为保留依据。

判断标准应当是：

1. 当前入口是否能到达。
2. 当前保留代码是否还在引用。
3. 当前生命周期是否依赖。

如果三个都不满足，默认删除。

### 3.3 只看文件名，不看调用链

同名目录或类似命名经常会误导判断。

真正有效的方法是：

1. 从入口出发看调用链。
2. 对关键符号做反查。
3. 用编译和测试验证删减后是否还能构建。

## 4. 推荐执行顺序

### 4.1 简版流程

1. 定入口。
2. 列能力。
3. 做符号反查。
4. 标出整套未接入子系统。
5. 先删整套子系统。
6. 再处理混合文件。
7. 编译验证。
8. 复查 `git diff` 和 `git status`。

### 4.2 每轮删减后的验证

至少要检查三件事：

1. `go test` 或等价构建是否通过。
2. 删除范围是否仍与入口可达性一致。
3. 是否误删了仍在用的共享 helper。

## 5. 可复用的删除标准

以下内容可以优先视为删除候选：

1. 没有从当前入口到达的整套 subsystem。
2. 只服务旧协议、旧路径、旧别名的兼容层。
3. 当前 binary 不再使用的管理面、诊断面、探活旁路。
4. 只剩定义、没有真实调用方的辅助模块。

以下内容不要轻易删：

1. 当前 tool 或 handler 正在用的业务逻辑。
2. 当前生命周期必需的基础设施。
3. 仍被其他保留文件引用的共享 helper。
4. 需要先迁移类型再删除实现的公共模型。

## 6. 经验沉淀

这类清理的本质是“缩小当前可达集”。

最有效的经验不是记住某个项目的目录，而是记住这条判断链：

1. 入口能不能到。
2. 能不能证明当前会执行。
3. 会不会影响当前能力或生命周期。
4. 能不能把活的 helper 留下，把死的 subsystem 一次删干净。

只要按这条链路做，清理速度通常会越来越快，误删概率也会更低。
